Ownership map:

- Assignment scope comes from `ROADMAP.md` plus the local `paN/README.md` files first. Current binary behavior is only a secondary observability check, because the shared implementation may over-accept features that the written milestone contract still marks undefined until a later PA.
- `PA10` owns pure syntax-tree construction and parser-shape fixes. A regression belongs here only if the structured AST dump is the first milestone that can observe the fix.
- `PA11` owns scopes, declarator-derived types, bindings, and constant/type lookup. It does not own procedural expression semantics.
- `PA12` owns ordinary expression semantics, overload resolution, conversions, call analysis, and control-flow statement semantics for the procedural subset.
- `PA14` owns procedural LowIR lowering once the PA12 semantic shape is already correct.
- `PA15` owns the first non-virtual object-model slice: class layout, member lookup/access, constructors/destructors, and basic class lowering.
- `PA17` owns polymorphic object-model behavior such as virtual dispatch, vtables, and polymorphic layout effects.
- `PA18` owns first-tier templates with type and template-template parameters, ordinary type parameter packs, and ordinary deduction/instantiation. Its README explicitly keeps non-type parameters, explicit specialization, partial specialization, and SFINAE out of scope.
- `PA19` owns the first metaprogramming slice: integral non-type parameters/arguments, explicit specialization of the supported subset, integral constant-expression template arguments, and `static_assert`. Its README still keeps partial specialization, SFINAE-heavy metaprogramming, and broader template machinery out of scope.
- `PA20` owns full `constexpr` / constant-evaluation semantics once the PA19 first slice is no longer enough.
- `PA21` owns the remaining standard template language once the PA18/PA19 subsets are no longer enough.
- `PA25` owns `auto` variable deduction, direct braced initialization of the supported scalar/array subset, captureless lambdas, and range-for over arrays/braced-init lists.
- `PA26` owns capturing lambdas, `std::initializer_list` interoperation, RTTI/`typeid`, and pointer-form `dynamic_cast`.
- `PA31` remains the future bucket for hosted/vendor extensions and hosted-source compatibility work that is implemented in the compiler but still outside the written PA10-PA30 assignment contracts.

Validated ownership notes:

- `HHC-160` should not stay in `PA11`. Current `pa11` (`cpptypes`) only records the function signature for `char16_t* f(char16_t* s, size_t n) { return s + n; }`, while current `pa12` (`cppcalls`) is the first milestone that actually dumps the `binary-expression ... OP_PLUS:+` semantics.
- `HHC-181` should not stay in `PA25`. Current `pa12` already accepts the scoped-enum/integral cast reduction semantically, while current `pa25` fails later with `ERROR: unsupported class initialization in PA26`, so the cast fix belongs to an earlier semantic milestone rather than the PA25 language-closure slice.
- `HHC-050` is a real `PA19` item once the roadmap/readme boundary is read carefully. Ordinary type parameter packs are already part of PA18; the owned feature in this case is explicit specialization over that earlier template form. The nearby `HHC-051` / `052` / `053` partial-specialization pack cases remain out of scope.
- `HHC-106` is a good example of why roadmap/readme scope wins over raw binary behavior. Current `pa11` can already print a class-scope function binding and current `pa12` can even dump `X::f(1)`, but the roadmap and `PA15` README put member lookup/method-call semantics in the first object-model milestone rather than the PA11/PA12 foundational slices. The current draft therefore should not be promoted blindly from `draft_regressions/pa11/`.
- `HHC-109` should not stay in `PA15` just because the hosted failure showed up in a class-construction spelling. `PA15` explicitly leaves temporary class-object materialization out of scope, and the current draft `throw E();` is doubly wrong because `throw` is `PA24` territory. The real regression needs a fresh PA16 value-semantics reduction.
- `HHC-111` should not stay in `PA14`. The current draft depends on user-defined `operator==` / `operator!=`, which first belongs to the PA16 value-semantics/operator layer. Current `cppvalue` still fails the draft at `a != b`, so the reduction also needs to be weakened to isolate the symbol-collision lowering bug instead of ordinary operator-resolution support.
- `HHC-114` is implemented in the compiler, but `PA14` still explicitly marks string literals out of scope. Until a later written milestone is chosen for ordinary string-literal lowering, this item should not be finalized into `pa14/tests`.
- `HHC-116` should not stay in `PA11`. The current reduction depends on class-template constant bindings plus `static_assert`, which only become part of the written contract in `PA19`, not the PA11 lookup/type foundation.
- `HHC-117` currently looks like a real `PA19` item, not a `PA31` one. The draft in `draft_regressions/pa31/` compiles cleanly in current `pa19`, and `PA19` is the first README that actually owns template-scope `static_assert` plus dependent metaprogramming lookup.
- `HHC-128` currently looks like a real `PA31` item, not a `PA10` one. Current `pa10` can parse the draft, but the source form is still GNU attribute syntax on a special member declaration, which is outside the written PA10 syntax contract and belongs in the future hosted-extension bucket.
- `HHC-075` should not stay in `PA26`. Old/current `pa10` already diverge at AST shape (`opaque-declaration` vs structured `function-definition`), so the earliest written owner is the PA10 parser boundary.
- `HHC-090` should not stay in `PA25`. PA10 already parses the trailing-return form correctly; the first milestone that actually rejects the function-template declaration semantically is `PA18`, so that is the earliest written owner.
- `HHC-093` should not stay in `PA31`. It is ordinary single-inheritance virtual override matching, which belongs to PA17’s documented polymorphic object-model slice.
- `HHC-026` should not stay in `PA31`. Class-template constant bindings consumed by `static_assert` are part of PA19’s documented metaprogramming surface.
- `HHC-012`, `013`, and `030` are good candidates for an expanded `PA11` handout boundary, but current `cpptypes` still fails the straightforward reductions even though current `cppmeta` accepts them. They should be treated as live contract-expansion blockers rather than already-finished PA11 regressions.
- `HHC-014` and `017` now show a split story: the old/current parser already diverges in `PA10`, so durable parser regressions can live there today, but the stronger PA11 semantic handout expansion would still need follow-up because current `cpptypes` rejects the semantic reductions.
- `HHC-069` should not stay in `PA31`. The core feature is ordinary `static_cast<ptr>(nullptr)` acceptance, which belongs to PA12 cast semantics; the hosted alias-declaration form was only the trigger.
- `HHC-108` should not stay in `PA31`. Source `throw` belongs to PA24, but the current PA24 harness in this repo is still LowIR/object driven rather than source-driven, so there is no assignment-local source regression slot for it yet.
- `HHC-027` still lacks a clean written earlier owner: PA15 explicitly excludes conversion operators, and current PA16 still rejects the ordinary `operator int() const noexcept` reduction.
- `HHC-190` and `HHC-258` are the clearest first residents of the new `PA20` bucket. They are ordinary standard constant-evaluation cases, not hosted/vendor compatibility.
- `HHC-080`, `HHC-198`, and `HHC-213` should stay in `PA31` despite the new `PA20` bucket, because `if constexpr` and alias-init `if constexpr` are still post-C++11 hosted-compatibility work under the current handouts.
- `HHC-076`, `HHC-078`, `HHC-193`, `HHC-220`, `HHC-221`, and `HHC-222` should route to `PA21` for ownership, but their current draft reductions use `inline` variable-template spellings. Final placement should reduce that syntax if we want the PA21 handout to stay precise about what part of the post-PA19 template surface is being tested.
