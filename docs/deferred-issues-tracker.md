# Deferred Issues Tracker

This document collects known deferred bugs, temporary workarounds, and
transitional gaps that were previously scattered across other docs and
trackers.

Its purpose is:

- to keep the remaining deferred issues visible in one place
- to ensure each item is revalidated before more work is done
- to prevent temporary workarounds from silently becoming permanent

This tracker is intentionally **not** the place to duplicate issues that
already have their own active plan document. If a deferred item is already
owned by a dedicated plan in [`docs/`](/Users/vishvananda/cppgm/docs), keep the
design and execution details in that plan and track it through
[plan-implementation-tracker.md](/Users/vishvananda/cppgm/docs/plan-implementation-tracker.md)
instead of repeating it here.

## Working Process

For each item in this tracker, follow this loop.

### 1. Revalidate First

Before planning or fixing anything:

1. Re-read the source note that originally recorded the issue.
2. Reproduce the issue on current `main`, or confirm the workaround/gap is
   still present in the current code.
3. Record the current behavior:
   - still reproduces
   - no longer reproduces
   - partially reproduces / changed shape

If the issue no longer reproduces:

- do not keep treating it as active debt
- mark it `resolved` or `stale`
- record what changed and where the apparent fix came from, if known

### 2. Re-Scope The Real Owner

If the issue still exists:

1. decide the earliest real owner assignment or subsystem
2. distinguish the real compiler bug from the current workaround symptom
3. avoid fixing only the bootstrap/frontier symptom when an earlier owner can
   carry the real regression

### 3. Plan The Real Fix

Before editing code:

1. write down the intended invariant
2. identify the workaround that should disappear after the fix
3. identify the durable regression surface that should remain after the fix

The goal is:

- real fix first
- owner regression second
- workaround removal third

not:

- keep the workaround
- patch around the current source line again

### 4. Land The Fix

For an active item:

1. add or restore the earliest owning regression
2. implement the real fix
3. remove the workaround if the fix fully covers it
4. run the relevant owner tests and any larger validation that the item needs
5. update this tracker with the outcome

### 5. Close Or Narrow The Item

When done:

- if fully fixed, mark `completed`
- if partially fixed, rewrite the tracker entry so it only describes the
  remaining gap
- if the broad issue split into a narrower remainder, create a follow-up plan
  and point to it here

## Status Key

- `todo`: not yet revalidated on current `main`
- `active`: revalidated and still present
- `blocked`: still present, but blocked on another prerequisite
- `completed`: fixed and no longer active
- `stale`: no longer reproduces or no longer appears to be real debt
