# v6sol performance comparison, 2026-10-31

Independent-source immediate multiplication is a useful small addition to the
reference backend. A broader interval-combination prototype did not pay for
its extra compiler work. Most other mechanisms in v6sol already have reference
counterparts, although their representations and policies differ substantially.

The reference baseline is `3d392d1904f0f8c054da1898030a63f5b7ab3af2`;
v6sol is pinned at `d53783ff83193c0f7d4ee1b8a798a2b8a3ca6bfc`. Active
uncommitted work in v6sol was excluded. A detached worktree was used for the
comparison and removed after preserving its sources, binaries and metadata.

## Method and boundaries

Both seeds use GCC 15.2.0 with
`-std=gnu++11 -Wall -O3 -fno-strict-aliasing` and identical standard-library
flags. Each seed builds its own compiler at O3. O0/O3 in the tables below refer
to compiling the frozen PA35 input with those binaries. They are not timings
of a complete compiler rebuild.

The shared input manifest SHA256 is
`2b1edfeb32a8658c2fc607c6a251da8840af349e0fd9e54aa45f8355013959b6`,
and the host-header closure is
`39b8f94e3bd4802ce3d974795ee74bd476c56e1e023a88eb114820a24bcf3fb3`.
The machine is an Intel Xeon E5-2696 v4. Immutable binaries, pinned cores,
two A/A calibration blocks and alternating ABBA/BAAB blocks were used.
User hardware counters measure whole-process instructions; separate page-table
observations measure RSS. Exact Callgrind attribution identifies the compiler's
own code and out-of-line calls. Those boundaries are reported separately.
Raw observations, commands, profiles, source prototypes and hashes remain in
the local Boost workspace's `validation/20261031-v6sol-perf` directory.

Outputs must reproduce byte-for-byte within each compiler. Each implementation's
seed/self pair and the constant-source codegen comparisons also verify identical
objects across the pair. Cross-implementation objects are not required to match.
Shared-machine wall-time and cycle noise prevent a sub-percent speed claim.
These results describe this workload, not a general compiler ranking.

## Frontend and generated code

| v6sol GCC seed / reference GCC seed | O0 | O3 |
| --- | ---: | ---: |
| Whole-process hardware instructions | 3.612936 | 2.340307 |
| Peak RSS | 3.531868 | 3.888094 |

The v6sol O0 profile spends about 16.4% of sampled self cycles in `Lexer::unit`,
followed by semantic interning, syntax instantiation and parser lookahead.
At O3, optimizer value numbering, memory forwarding and instruction-vector
construction also become prominent. These are individual profile shares, not
complete phase-time measurements.

Its statistics record about 1.25 million syntax nodes in roughly 90 MB of node
slabs, plus 32 MB of scopes and 34 MB of types. The reference's typed AST,
role-specific entities, interned types, arenas and lexer fast paths already
address the relevant architectural concerns. Importing the student's generic
handle and sparse-record model would require evidence beyond its local savings
against its own earlier implementation.

At O3, v6sol's self binary makes about 25.7 million more out-of-line string-copy
calls, 24.2 million more calls to each of `Lexer::physical` and `Lexer::phase1`,
and 8.5 million more LowIR instruction-copy calls. Its dynamic mix adds roughly
790 million immediate moves, 781 million register copies, 746 million extensions,
718 million frame loads and 687 million push/pop instructions. Attribution
moves when GCC inlines a function; a zero out-of-line count does not mean its
work vanished. This is evidence of codegen/inlining costs in addition to its
larger frontend workload.

## Candidate review

The reference already has address rematerialization across uses, typed load
folding, copy-to-LEA fusion, constant-store merging, Boolean/extension cleanup,
loop-sensitive and partial inlining, frame omission, shrink wrapping and global
register allocation. v6sol's exact preservation regions and residual-callee
policies differ, but are not small independent substitutions. Its return planner
shares long epilogues to save text; that introduces return-path jumps compared
with the reference's optimized duplicated epilogues. No such policy was copied
without measurement.

The interval prototype combines direct predicates on one immutable input using
a modular subtraction and unsigned comparison. Adapting it exposed a pipeline
difference: the reference forms short-circuit selects late, so checking only
its earlier And/Or expressions misses ordinary source ranges. The revised
prototype also checks selects where they are constructed, captures use counts
once, and performs no recursive matching or per-insertion whole-function scan.
Original student controls match GCC and the baseline at O0–O3, including signed
limits, volatile reads and calls that change memory. A small range function
shrinks from eight to seven native instructions.

It still adds **0.270%** to seed O3 instructions. An unchanged-source compiler
rebuilt with it improves only **0.008% at O0 / 0.001% at O3**. The frozen workload
does not repay the new optimizer work, so the prototype is rejected and its
source remains outside the implementation.

## Retained immediate multiplication

An immediate IMUL can read a register or memory source independently of its
destination. The reference previously copied or loaded the source into the
result before the multiply. Selection now exposes the three actual operands
to MIR and the encoder uses the existing independent-source encoding. Existing
LEA/shift choices for cheap factors remain intact.

A memory operand must have the arithmetic instruction's exact access width.
Review caught an initial prototype widening a 32-bit load to 64 bits. A packed
input with nonzero neighboring data exposes the wrong widened result; it fails
on that prototype and passes with the final guard. The flawed version was never
committed, and its partial validation and measurements are marked superseded.
Register sources retain their existing canonical-value handling.

The required PA33 fixture checks register and memory forms, the width boundary,
a large unsigned 32-bit multiplier, a 64-bit constant beyond imm32, volatile
reads and a read preceding a store. The baseline passes its behavior but fails
the two copy/load-elimination budgets. The rejected width prototype fails the
behavior guard. References are generated through the ordinary PA33 worker.

The corrected candidate's final six-block comparisons are:

| Candidate / reference baseline | Instructions O0 | Instructions O3 | Peak RSS O0 | Peak RSS O3 |
| --- | ---: | ---: | ---: | ---: |
| GCC seed | 1.000002 | 0.999952 | 0.999587 | 0.999393 |
| Unchanged-source generated compiler | 0.999687 | 0.999082 | 0.999893 | 1.000696 |
| Self binary, including source change | 0.999708 | 0.999049 | 1.000309 | 1.000207 |

Every paired block passes the instruction +0.5% and RSS +3% regression limits;
A/A instruction noise is below the observed codegen improvement. Final seed and
self outputs are byte-identical at both levels. This is approximately a 0.03%
O0 / 0.095% O3 reduction in self-built compiler instructions, with seed work and
RSS effectively flat. It is not an elapsed-time claim.

Required local correctness, export and CI results are recorded with the PR.
The width counterexample and the baseline instruction-budget negative control
are retained alongside every measurement.
