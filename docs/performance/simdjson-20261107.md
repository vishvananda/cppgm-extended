# simdjson compatibility and SSE performance, 2026-11-07

The reference compiler builds unmodified simdjson v5.1.1's scalar fallback and
Westmere SSE backend. The initial SSE build was correct but several times slower
than GCC. Preserving vector operations through inlining and copies removes most
of that deficit. The explicit Westmere profile below reaches 0.85× GCC on
`twitter.json` and 0.83× on `citm_catalog.json`; parity is still open.

All ratios below are reference time / cppgm time: **higher is better**.
These are library build and hot DOM parse measurements, not whole application
builds or cold-input throughput.

## What caused the large SSE deficit

The compatibility baseline is the frozen compiler with SHA256
`e151cdb924c69e32dd6cb4f78984500eeff75e4809024166313b7fbc9b06ac52`.
On the Intel Xeon E5-2696 v4 investigation host, that build measured about
0.123× GCC on Twitter and 0.192× on CITM. Those diagnostic measurements used
the upstream parse driver, adapted only to expose its mean parse time. They
are not a paired comparison against the later EPYC run.

Three general representation problems accounted for most of the lost time:

- Intrinsic selectors became constant only after required wrapper inlining.
  Lowering had already expanded the operation into scalar work. Deferred typed
  operations now survive that boundary and select the vector form when the
  selector is proved constant. Truly variable selectors retain a correct
  ordinary LowIR fallback. Constant packed-shift counts also select immediate
  forms, including the defined oversized-count behavior.
- Byte and word vector lists used consecutive narrow stack stores followed by
  a wide vector reload. This introduced costly store-forwarding dependencies
  in the SIMD loops. Full 128-bit narrow lists now assemble lane bits in
  registers, preserving source evaluation order and signed lane bit patterns.
- Aggregate splitting and copy forwarding lost whole-vector values. Typed
  vector fields now remain vector loads, stores and forwarded values rather
  than scalar memory round trips.

The implementations use typed operations, values, layouts and proven constants.
They do not recognize simdjson function names, source text or benchmark inputs.
The reducers check semantics, evaluation order and broad optimization outcomes;
they do not demand one exact instruction sequence.

A fixed Callgrind probe over Twitter and CITM falls from 374,331,919 instructions in the
compatibility baseline to 266,128,437 after the vector fixes, a 28.9% reduction.
GCC uses 226,261,602 in that probe. Instruction totals do not explain the much
larger initial wall-time deficit by themselves: the eliminated narrow-store /
wide-reload dependency was also costly per instruction.

The later Intel run using the CI harness reports SSE ratios of 0.874× GCC for
Twitter and 0.786× for CITM, but has calibration warnings and overlapping host
activity. Retain it as diagnostic evidence; the clean EPYC run above is the
stronger timing result. Local compile ratios are about 4.4× GCC and 2.4× Clang
for SSE, consistent with the CI result's large compile-time advantage.

## Scalar register pressure experiment

The remaining profiles expose a general allocation opportunity: long retained
scalars compete with short, frequently used loop values. A private candidate
ranked scalar candidates by weighted uses per occupied live-range slot, keeping
the existing XMM policy. With one fixed GCC-built driver, one warmup parse and
16 measured parses per input, Callgrind counts fell as follows:

| Input | After vector fixes | Allocation candidate | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 86,230,499 | 84,202,496 | 2.35% |
| CITM | 217,441,619 | 209,418,533 | 3.69% |

Canonical JSON remained identical. An independent reduced program keeps eight
values live across a numeric loop; the candidate removed five repeated frame
accesses inside that loop. Its retained behavior test covers empty input, an
early nondigit, bounded and overflowing arithmetic, and every switch path,
without prescribing registers or opcodes.

This policy is **not included** in the final compiler. An
[EPYC 9V74 run](https://github.com/vishvananda/cppgm-extended/actions/runs/42362475135)
reported SSE ratios of 0.905× / 0.909× GCC, but scalar ratios of only
0.809× / 0.731×, compared with the earlier 0.946× / 0.854×. Those are separate
CI runs, not a direct A/B, so they do not establish an exact regression size.
They are sufficient reason to withhold the policy pending a controlled
comparison. The Intel investigation showed fewer scalar instructions and faster
local execution, which does not establish a benefit on EPYC.

The six existing native quality kernels, self-hosting and PA35 release gates
passed the experiment. Those checks did not capture the scalar timing concern.
Keep scalar and SIMD workloads in the runtime comparison: reducing instruction
counts or spills alone does not guarantee a faster program.

## Explicit Westmere instruction profile

The SSE benchmark now passes `-mpopcnt` to all three compilers. Westmere's
source already requests SSE4.2, PCLMUL and POPCNT; an explicit target option
lets our compiler retain population count as a typed operation and select
its native form. Scalar compilation keeps the baseline ISA. At the target-option
revision `9e248f3f2`, disabling it reproduced both prior library objects byte for
byte; the separate arithmetic follow-up below changes their selected code.

Using the same fixed-driver Callgrind probe as the allocation experiment:

| Input | Portable population count | Explicit POPCNT | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 86,230,499 | 83,310,429 | 3.39% |
| CITM | 217,441,619 | 208,265,687 | 4.22% |

Both canonical outputs agree. The default frozen compiler workload changes by
less than 0.002% in executed compile instructions against the prior validated
build. Local paired cycle counts suggest an additional gain, but A/A drift
prevents a precise timing claim. The EPYC table near the top records the
explicit profile and identifies its flags and measured revision.

The option defaults off; `-mno-popcnt` disables it and the last target option
wins. `__POPCNT__` reflects the selected target, with ordinary command-line
macro overrides. The optional PA29 target-feature suite checks widths, zero,
argument evaluation and all compiler routes without requiring one instruction
sequence. Required course reports retain the baseline target.

## Scaled arithmetic follow-up

Another general selection gap occurs when a multiply or shift feeds an add.
The encoder selected a scaled address and shift for the multiply, then a
separate add. The native cleanup can combine the final scale with the add,
using a second address calculation only when an odd factor also needs one.
It preserves the operation width, wrapped bits, intermediate readers and live
flags, and bounds its local searches. No source or function names are involved.

With the explicit POPCNT profile and the same fixed driver:

| Input | Before scaled arithmetic | After | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 83,310,429 | 83,155,144 | 0.19% |
| CITM | 208,265,687 | 206,015,626 | 1.08% |

Both canonical JSON outputs agree. Scalar counts also fall, by 0.11% / 0.70%.
The frozen compiler workload's O3 compile cost increases by 0.019% against
the explicit-POPCNT compiler, while its O0/O3 output objects remain identical.
The behavior reducer checks multiple scale factors, 32/64-bit widths, overflow,
retained intermediate values and result-dependent conditions across all routes;
it prescribes no registers or opcodes.

## Remaining opportunities

The explicit-profile EPYC results imply about 17% and 21% more CPU time than GCC for the
SSE parses. Profiles and emitted code point to register moves, frame-home
traffic and scalar digit-parsing loops. The register allocator's work-budget
fallback was checked and is not firing in the two main parsing stages.

Function-local target pragmas remain a possible extension. The explicit
POPCNT option is a whole-translation-unit ISA choice; automatically selecting
optional instructions inside a dispatched function needs corresponding
function-level target facts.

Two small native experiments were rejected: clearing bit-scan destinations to
break dependencies, and folding aligned frame operands into packed binary
operations. Paired local measurements showed no repeatable improvement. Their
extra instructions or complexity are not included in this branch.

Further work should reduce typed live ranges and redundant frame traffic,
then evaluate target-feature-aware scalar instructions. Each change needs
paired measurements against the frozen compiler, GCC and Clang, plus the
existing course performance gates. The CI job records performance on every
commit without hiding slowdowns behind a speed threshold.

## Correctness and course boundaries

Compatibility fixes cover specialized member templates, whole-vector braced
initialization, XGETBV, missing vector builtins, constant-false template
recursion, aggregate default member initializers and template range-for lookup.
The broader library matrix additionally exposed initialized lambda captures
and Clang vector scalar casts; each has focused reducers.

C++14/17 features remain in the optional `modern-cxx` student lanes, with
concise optional handout guidance. C++11 remains the required course dialect.
On the frozen `semantic_overload.cpp` compiler workload, Cachegrind counts
3,307,097,251 instructions at O0 and 9,515,380,677 at O3. Against the original
compiler's A/A measurements (3,302,784,078 / 3,302,784,155 at O0 and
9,508,898,606 / 9,508,898,560 at O3), this is about +0.13% and +0.07%. That
is a workload-specific compile-cost sanity check, not a whole-suite bound.

The compiler changes have been checked with the strict assignment report,
debug-info tests, self-host through PA5, inception identity, architecture and
placement audits, PA35 release gates and student-export validation. A selected
75-test upstream CTest suite exercises both cppgm-built simdjson and its clients
with Westmere forced. It excludes tests requiring unsupported C++20 facilities
or unavailable external datasets; this is not a claim of full upstream or
language-version conformance.
