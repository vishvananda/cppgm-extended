# simdjson compatibility and SSE performance, 2026-11-07

The reference compiler builds unmodified simdjson v5.1.1's scalar fallback and
Westmere SSE backend. The initial SSE build was correct but several times slower
than GCC. Preserving vector operations through inlining and copies removes most
of that deficit. Deeper profiling isolates pressure in large inlined functions
and discarded branch-likelihood information. Correcting one unnecessary frame
restriction improves local SSE CPU speed by 1.026×; parity is still open.

All ratios below are reference time / cppgm time: **higher is better**.
These are library build and hot DOM parse measurements, not whole application
builds or cold-input throughput.

## What caused the large SSE deficit

The compatibility baseline is the frozen compiler with SHA256
`e151cdb924c69e32dd6cb4f78984500eeff75e4809024166313b7fbc9b06ac52`.
On the Intel Xeon E5-2696 v4 investigation host, that build measured about
0.123× GCC on Twitter and 0.192× on CITM. Those diagnostic measurements used
the upstream parse driver, adapted only to expose its mean parse time. They
are not a paired comparison against the later EPYC run.

Three general representation problems accounted for most of the lost time:

- Intrinsic selectors became constant only after required wrapper inlining.
  Lowering had already expanded the operation into scalar work. Deferred typed
  operations now survive that boundary and select the vector form when the
  selector is proved constant. Truly variable selectors retain a correct
  ordinary LowIR fallback. Constant packed-shift counts also select immediate
  forms, including the defined oversized-count behavior.
- Byte and word vector lists used consecutive narrow stack stores followed by
  a wide vector reload. This introduced costly store-forwarding dependencies
  in the SIMD loops. Full 128-bit narrow lists now assemble lane bits in
  registers, preserving source evaluation order and signed lane bit patterns.
- Aggregate splitting and copy forwarding lost whole-vector values. Typed
  vector fields now remain vector loads, stores and forwarded values rather
  than scalar memory round trips.

The implementations use typed operations, values, layouts and proven constants.
They do not recognize simdjson function names, source text or benchmark inputs.
The reducers check semantics, evaluation order and broad optimization outcomes;
they do not demand one exact instruction sequence.

A fixed Callgrind probe over Twitter and CITM falls from 374,331,919 instructions in the
compatibility baseline to 266,128,437 after the vector fixes, a 28.9% reduction.
GCC uses 226,261,602 in that probe. Instruction totals do not explain the much
larger initial wall-time deficit by themselves: the eliminated narrow-store /
wide-reload dependency was also costly per instruction.

The later Intel run using the CI harness reports SSE ratios of 0.874× GCC for
Twitter and 0.786× for CITM, but has calibration warnings and overlapping host
activity. Retain it as diagnostic evidence; the clean EPYC run above is the
stronger timing result. Local compile ratios are about 4.4× GCC and 2.4× Clang
for SSE, consistent with the CI result's large compile-time advantage.

## Scalar register pressure experiment

The remaining profiles expose a general allocation opportunity: long retained
scalars compete with short, frequently used loop values. A private candidate
ranked scalar candidates by weighted uses per occupied live-range slot, keeping
the existing XMM policy. With one fixed GCC-built driver, one warmup parse and
16 measured parses per input, Callgrind counts fell as follows:

| Input | After vector fixes | Allocation candidate | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 86,230,499 | 84,202,496 | 2.35% |
| CITM | 217,441,619 | 209,418,533 | 3.69% |

Canonical JSON remained identical. An independent reduced program keeps eight
values live across a numeric loop; the candidate removed five repeated frame
accesses inside that loop. Its retained behavior test covers empty input, an
early nondigit, bounded and overflowing arithmetic, and every switch path,
without prescribing registers or opcodes.

This policy is **not included** in the final compiler. An
[EPYC 9V74 run](https://github.com/vishvananda/cppgm-extended/actions/runs/42362475135)
reported SSE ratios of 0.905× / 0.909× GCC, but scalar ratios of only
0.809× / 0.731×, compared with the earlier 0.946× / 0.854×. Those are separate
CI runs, not a direct A/B, so they do not establish an exact regression size.
They are sufficient reason to withhold the policy pending a controlled
comparison. The Intel investigation showed fewer scalar instructions and faster
local execution, which does not establish a benefit on EPYC.

The six existing native quality kernels, self-hosting and PA35 release gates
passed the experiment. Those checks did not capture the scalar timing concern.
Keep scalar and SIMD workloads in the runtime comparison: reducing instruction
counts or spills alone does not guarantee a faster program.

## Explicit Westmere instruction profile

The SSE benchmark now passes `-mpopcnt` to all three compilers. Westmere's
source already requests SSE4.2, PCLMUL and POPCNT; an explicit target option
lets our compiler retain population count as a typed operation and select
its native form. Scalar compilation keeps the baseline ISA. At the target-option
revision `9e248f3f2`, disabling it reproduced both prior library objects byte for
byte; the separate arithmetic follow-up below changes their selected code.

Using the same fixed-driver Callgrind probe as the allocation experiment:

| Input | Portable population count | Explicit POPCNT | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 86,230,499 | 83,310,429 | 3.39% |
| CITM | 217,441,619 | 208,265,687 | 4.22% |

Both canonical outputs agree. The default frozen compiler workload changes by
less than 0.002% in executed compile instructions against the prior validated
build. Local paired cycle counts suggest an additional gain, but A/A drift
prevents a precise timing claim. The EPYC table near the top records the
explicit profile and identifies its flags and measured revision.

The option defaults off; `-mno-popcnt` disables it and the last target option
wins. `__POPCNT__` reflects the selected target, with ordinary command-line
macro overrides. The optional PA29 target-feature suite checks widths, zero,
argument evaluation and all compiler routes without requiring one instruction
sequence. Required course reports retain the baseline target.

## Scaled arithmetic follow-up

Another general selection gap occurs when a multiply or shift feeds an add.
The encoder selected a scaled address and shift for the multiply, then a
separate add. The native cleanup can combine the final scale with the add,
using a second address calculation only when an odd factor also needs one.
It preserves the operation width, wrapped bits, intermediate readers and live
flags, and bounds its local searches. No source or function names are involved.

With the explicit POPCNT profile and the same fixed driver:

| Input | Before scaled arithmetic | After | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 83,310,429 | 83,155,144 | 0.19% |
| CITM | 208,265,687 | 206,015,626 | 1.08% |

Both canonical JSON outputs agree. Scalar counts also fall, by 0.11% / 0.70%.
The frozen compiler workload's O3 compile cost increases by 0.019% against
the explicit-POPCNT compiler, while its O0/O3 output objects remain identical.
The behavior reducer checks multiple scale factors, 32/64-bit widths, overflow,
retained intermediate values and result-dependent conditions across all routes;
it prescribes no registers or opcodes.

## Reading only the needed packed bits

The string path constructs a wide integer from narrow masks, then reads a
slice of it. The earlier simplifier could discard one wholly irrelevant OR
operand but could not project through the tree. The follow-up propagates the
defined result ranges of vector masks and projects a bounded integer OR tree
through a constant logical shift. It preserves original-width clipping,
other readers and effects, and estimates whether the rewrite removes work.
The existing operations and LowIR format are unchanged.

| Input | After scaled arithmetic | After bit projection | Reduction |
| --- | ---: | ---: | ---: |
| Twitter | 83,155,144 | 81,556,738 | 1.92% |
| CITM | 206,015,626 | 204,187,619 | 0.89% |

A [controlled EPYC 7763 comparison](https://github.com/vishvananda/cppgm-extended/actions/runs/42375605482)
builds both frozen compilers on one host and links each library with the same
GCC-built driver. Five paired blocks measure **1.0312× / 1.0222×** CPU speed
against the arithmetic revision. A/A calibration for those pairs stays within
0.7%. The scalar library object is byte-identical; its timings are unchanged.
The comparison with Clang on scalar CITM has a calibration warning; that pair
does not support a precise speed claim.

The new analysis starts with cheap opcode and producer checks. This reduces
its extra compile instructions on the frozen O3 workload from 0.83% in the
prototype to **0.008%**, without changing the emitted objects. The behavior
test covers masked and clipped fields, shared values, 32/64-bit results,
vector masks and discarded result bits with retained effects. It uses an
independent bit-by-bit oracle rather than an instruction-sequence check.

## Frequency-floor experiment

Another private candidate applies the allocator's minimum warm-block flow
before estimating loop repetition. This keeps both numeric induction values
in registers and removes further instructions, but the
[controlled comparison](https://github.com/vishvananda/cppgm-extended/actions/runs/42373564932)
finds SSE gains of 1–4% alongside scalar CPU ratios of 0.9065× / 0.8230×
against the arithmetic revision: roughly 10% / 22% more time. It is excluded.
Correctness, the quality kernels and lower instruction totals did not predict
that timing tradeoff.

## Constant materialization and pressure experiments

Cycle sampling on the local Xeon puts about 53% of the retained compiler's
parse cycles in stage 2, versus about 48% for GCC. This is a diagnostic sample,
not a paired phase timing. Disassembly exposes repeated constant-vector
construction as well as frame traffic in digit-parsing loops.

A private trial replaces known integer vector construction with pooled loads,
while retaining shared results in registers. It reduces the fixed-driver SSE
instruction counts from 81,556,738 / 204,187,619 to 79,709,640 / 201,473,224.
However, the [controlled EPYC comparison](https://github.com/vishvananda/cppgm-extended/actions/runs/42381784689)
measures CPU ratios of **1.0028× / 0.9892×** against the retained compiler:
flat on Twitter and about 1% slower on CITM. Adding proactive splitting of
unused live-through values gives **0.9974× / 1.0050×** against the retained
compiler. These SSE pairs have no A/A warning above 2%; some scalar pairs do.
Neither trial is included. Fewer instructions and a cleaner digit loop did
not establish a useful whole-parse speedup.

A more selective allocator trial attempts to release an unused live-through
register only after another loop value actually fails allocation, with exact
rollback when that fails to help. Its [controlled EPYC 9V74 run](https://github.com/vishvananda/cppgm-extended/actions/runs/42383567884)
measures SSE CPU ratios of **1.0010× / 1.0089×**, but scalar ratios of
**0.9732× / 0.9873×** against the retained compiler. No pair has an A/A warning
above 2%. This policy is excluded too. The candidate's 0.956× / 0.948× SSE
ratios against GCC on this newer CPU cannot be compared directly with the
older EPYC 7763 runs; its paired gain over unchanged code is small.

## Remaining opportunities

The controlled bit-projection run still uses about 15% and 17% more CPU time
than GCC for the SSE parses. Profiles and emitted code point to register moves, frame-home
traffic and scalar digit-parsing loops. The register allocator's work-budget
fallback was checked and is not firing in the two main parsing stages.

Function-local target pragmas remain a possible extension. The explicit
POPCNT option is a whole-translation-unit ISA choice; automatically selecting
optional instructions inside a dispatched function needs corresponding
function-level target facts.

Two small native experiments were rejected: clearing bit-scan destinations to
break dependencies, and folding aligned frame operands into packed binary
operations. Paired local measurements showed no repeatable improvement. Their
extra instructions or complexity are not included in this branch.

Further work should reduce typed live ranges and redundant frame traffic,
then evaluate target-feature-aware scalar instructions. Each change needs
paired measurements against the frozen compiler, GCC and Clang, plus the
existing course performance gates. The CI job records performance on every
commit without hiding slowdowns behind a speed threshold.

## Isolating the remaining gap

A [controlled phase comparison](https://github.com/vishvananda/cppgm-extended/actions/runs/42387135801)
on EPYC 7763 separates structural scanning (stage 1) from tape construction
(stage 2). It uses the retained `235d3d8f3` compiler, pinned upstream inputs,
one fixed GCC-built caller, output equality, paired blocks and A/A calibration.
The cppgm phase comparisons have no calibration warnings above 2%.

| Input | Stage 1 CPU speed vs GCC | Stage 1 instructions / GCC | Stage 2 CPU speed vs GCC | Stage 2 instructions / GCC |
| --- | ---: | ---: | ---: | ---: |
| Twitter | 0.873× | 1.018× | 0.879× | 1.281× |
| CITM | 0.875× | 1.048× | 0.836× | 1.253× |

Instruction counts come from separate local Callgrind profiles of sixteen
phase-only parses, excluding warmup. Final totals agree with Callgrind's
collected events. These are instruction ratios, not timing predictions.

Stage 1 has relatively little extra instruction work but considerably more
vector memory traffic. For sixteen CITM scans, its main scanning function
executes about 10.0 million stack-vector loads, versus 1.7 million for GCC
and 0.43 million for local Clang 22. These include spilled live values and
unchanged masks repeatedly loaded within a block. Counting instructions alone
misses the extra load dependencies. This is a concrete allocation and local
reuse opportunity; an earlier constant-pooling experiment did not improve
paired runtime, so fewer loads still need a timing check.

Stage 2 performs substantially more work per JSON value. Synthetic arrays of
short strings, numbers and small objects require 22–35% more instructions
than GCC; long and escaped strings require only 4–6% more. These diagnostic
families are retained as independent input shapes, without source-specific
optimizer rules. In the hot integer-digit loop, cppgm's repeated body uses
twelve instructions versus nine for GCC, counting the taken loop path
and excluding its exit jump. The dominant cppgm body executes 1.65 million
times across sixteen CITM parses. Loop peeling and separate number paths
prevent multiplying that difference into an exact whole-phase attribution,
but spill stores, register transfers and loop-carried value placement are
concrete targets.

Two local source ablations isolate further missing inputs. Outlining only
`parse_number` reduces cppgm's stage 2 instruction ratio against equivalently
outlined GCC from 1.28× to 1.11× on Twitter and from 1.25× to 1.05× on
CITM. Its isolated digit loop then uses nine instructions and no stack spill.
A short paired CITM run improves cppgm's stage 2 CPU time by 6.6%, with
A/A variation below 1.5%. This modified-source experiment diagnoses the
interaction between function size and allocation; it is not an upstream
benchmark result or a proposal to recognize this function.

Removing only `simdjson_likely` / `simdjson_unlikely`, while preserving their
value, type and evaluation, makes local GCC and Clang stage 1 slower on CITM
by about 7.2% and 8.0%. Those comparisons have A/A variation below 1.5%.
The cppgm object is byte-identical with and without the hints: its current
lowering discards them. Preserving advisory likelihood information for
allocation and layout is therefore a concrete missing optimization input.
Hints must never justify deleting a defined path. A first private prototype
propagates them to allocation and layout, but does not give a consistent
runtime gain across scalar and SSE, so it is excluded. The reference ablation
shows the value of the information to competing compilers; it does not prove
that propagating it alone reproduces their downstream decisions.

Counterfactual compiler builds constrain the diagnosis:

- Reserving GCC's two extra GPRs and two extra XMM registers raises stage 2
  instruction work by only 3–4%, far below cppgm's 25–28% excess. Register
  capacity alone does not explain the gap.
- Disabling GCC's local scalar replacement raises stage 2 instruction work
  by 13% on Twitter and 7.5% on CITM; disabling only its interprocedural
  counterpart changes neither object nor counts. However, cppgm's optimized
  LowIR already promotes the main iterator and tape-builder objects. The
  remaining distinction needs to be traced through smaller copies and
  allocation, rather than inferred from a pass name.
- GCC stage 2 changes little when PRE/FRE, loop motion or strict-aliasing
  assumptions are disabled individually. Clang's basic allocator costs
  about 25% stage 2 CPU time compared with its default allocator, confirming
  that allocation quality can matter much more than the register count.

A [separate encoding-only probe](https://github.com/vishvananda/cppgm-extended/actions/runs/42390032823)
replaced cppgm's bit-scan encoding with compatible REP-BSF/TZCNT. It did not
improve paired runtime and is not retained. Similarly, a predecessor worklist
lets dead-frame-store analysis finish within its existing budget on the large
stage 2 functions, but the newly removed stores are cold. That analysis
improvement does not by itself close the runtime gap. The hot digit-loop
reload is forwarded later by the encoder, so removing its apparent spill
requires changes before or across that boundary.

The remaining deficit is concentrated in high-pressure vector code and
per-value work inside large inlined functions. Existing-suite averages near
parity do not establish parity for these shapes. Every retained change still
needs paired runtime measurements and the existing correctness and
performance gates.

## Wide integer conversions unnecessarily reserved a register

The allocation trace identifies a concrete restriction: a loop pointer cannot
obtain a register at its entry transfer because all twelve allocatable GPRs
are occupied. RBP is unavailable even though the final machine code omits its
frame pointer. The earlier eligibility scan rejects every LowIR conversion
involving `i128`, including integer extensions and truncations. Their selected
forms only move integer bits; a high-product chain may fold them into an
ordinary multiply. They do not require the stack adjustment of a genuine
128-bit floating conversion.

Commit `ad039b8d9` keeps RBP available for those integer conversions, while
retaining the restrictions for actual floating conversions, dynamic stack
allocation, variadic state and call argument areas. This uses the selected
operation's requirements, without recognizing a library or tuning a workload
threshold.

On the local Xeon E5-2696 v4, immutable old/new libraries linked to one fixed
GCC caller give the following full-parse measurements:

| SSE input | CPU speed vs `235d3d8f3` | Cycle ratio | Instructions before | Instructions after |
| --- | ---: | ---: | ---: | ---: |
| Twitter | 1.026× | 1.031× | 81,556,738 | 79,595,405 |
| CITM | 1.026× | 1.036× | 204,187,619 | 200,124,907 |

The timing uses seven ABBA/BAAB blocks, two A/A blocks before and after,
a pinned core and at least 0.5 seconds of baseline parse CPU per observation.
All observations are retained in `optimization/deep-analysis/rbp-live1-cycles-final1/`.
SSE A/A variation stays within 0.7% for cycles and 1.9% for CPU time.
Instruction totals use the existing sixteen-iteration benchmark driver, with
its warmup included, and canonical output agrees. These are local gains over
the retained compiler, not new EPYC ratios against GCC or Clang.

A fresh direct comparison on the same Intel host uses GCC 15.2 and Clang
22.1.2, the same explicit SSE/POPCNT profile and one fixed GCC caller:

| SSE input | CPU speed vs GCC | CPU speed vs Clang | Cycles vs GCC | Cycles vs Clang |
| --- | ---: | ---: | ---: | ---: |
| Twitter | 0.946×* | 0.935× | 0.936× | 0.937× |
| CITM | 0.899× | 0.945× | 0.900× | 0.938× |

These ratios are higher-is-better. Five paired blocks and two A/A blocks
before and after use at least 0.5 seconds of reference parse CPU per
observation. *The Twitter/GCC CPU calibration drifts by 2.4%; treat that CPU
ratio as approximate. All other CPU calibrations stay within 1.2%, and cycle
calibrations within 0.3%. Raw data, input hashes and immutable binary hashes
are retained in `optimization/deep-analysis/rbp-live1-references-local1/`.
The remaining local gap is about 6–11% in runtime; parity is still open.

Scalar instruction work falls by 1.3–1.6%; its local cycle ratios are within
0.3% of unchanged. Scalar calibration is noisier, so this run does not support
a precise scalar runtime change. On the frozen compiler workload, O0 compile
instructions are effectively unchanged and O3 falls by 0.003%; the O0 emitted
object is byte-identical. A self-checking course fixture uses an independent
32-bit-part multiplication oracle, live loop state, signed widening and actual
128-bit floating conversions. It checks behavior across driver/backend routes,
without requiring a register or instruction sequence.

## Correctness and course boundaries

Compatibility fixes cover specialized member templates, whole-vector braced
initialization, XGETBV, missing vector builtins, constant-false template
recursion, aggregate default member initializers and template range-for lookup.
The broader library matrix additionally exposed initialized lambda captures
and Clang vector scalar casts; each has focused reducers.

C++14/17 features remain in the optional `modern-cxx` student lanes, with
concise optional handout guidance. C++11 remains the required course dialect.
On the frozen `semantic_overload.cpp` compiler workload, Cachegrind counts
3,307,100,237 instructions at O0 and 9,515,852,313 at O3. Against the original
compiler's A/A measurements (3,302,784,078 / 3,302,784,155 at O0 and
9,508,898,606 / 9,508,898,560 at O3), this is about +0.13% and +0.07%. That
is a workload-specific compile-cost sanity check, not a whole-suite bound.

The compiler changes have been checked with the strict assignment report
(8,097/8,097), debug-info tests, self-host through PA5, inception identity,
architecture and placement audits, all seventeen PA35 release gates and a fresh
student export matching 22,672 portable reference outputs. A selected
75-test upstream CTest suite exercises both cppgm-built simdjson and its clients
with Westmere forced. It excludes tests requiring unsupported C++20 facilities
or unavailable external datasets; this is not a claim of full upstream or
language-version conformance.
