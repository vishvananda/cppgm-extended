# PA38 PA10 Frontier Convergence Plan

Archive note: this convergence plan has been folded into the maintained PA38
`test-through-*` validation surface. Keep it as historical execution context,
not as the active workflow.

## Goal

Drive the current `pa38` self-host frontier through `pa10` in two separate
lanes:

- a Homebrew clang-built `cppgm++` lane, which is the first `test-through-pa10`
  frontier to run after each clean checkpoint
- a Homebrew GCC-built `cppgm++` lane, which validates every fix that changes
  compiler behavior and catches GCC/libstdc++-specific hosted-header fallout

Completion means:

- `cppgm++-self` builds successfully through the `pa38` staged self-host
  wrapper in both lanes
- every `pa1` through `pa10` test run driven by the staged self-built tools
  passes
- LowIR tests use direct text comparison, not relaxed metadata
  canonicalization
- every discovered real compiler bug has a minimal regression in the earliest
  owning PA
- each coherent fix batch is committed before moving to an unrelated frontier
  failure
- any fix discovered in one lane is validated in the other lane before it is
  considered closed

This plan follows the same convergence discipline as
[`pa34-pa35-convergence-plan.md`](../pa34-pa35-convergence-plan.md), but the
discovery surface is `pa38 test-through-pa10` rather than hosted `pa34`/`pa35`.

## Dual-Lane Baseline

Keep the two PA38 frontier lanes physically separate. Either use two worktrees,
or use one worktree with separate compiler binaries and object roots. Do not let
the GCC lane reuse clang-built PA38 objects, and do not let the clang lane reuse
GCC-built PA38 objects.

The default single-worktree layout is:

```sh
CLANG_CXX=/usr/local/opt/llvm/bin/clang++
GCC_CXX=/usr/local/opt/gcc/bin/g++-15

CLANG_PA38_OBJ=../obj/pa38-clang
GCC_PA38_OBJ=../obj/pa38-gcc15
```

Build the clang lane first and run `test-through-pa10` there:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 \
make -C pa38 test-through-pa10 \
  CXX=../dev/cppgm++ \
  CPPGM_HOST_CXX="$CLANG_CXX" \
  PA38_OBJ_ROOT_BASE="$CLANG_PA38_OBJ"
```

Build the GCC lane with a GCC-built `cppgm++` binary and a distinct object root,
then run the same PA38 frontier:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 \
make -C pa38 test-through-pa10 \
  CXX=../dev/cppgm++ \
  CPPGM_HOST_CXX="$GCC_CXX" \
  PA38_OBJ_ROOT_BASE="$GCC_PA38_OBJ"
```

If a separate worktree is used, keep the same split concept: each worktree gets
its own `dev/cppgm++` built by the intended host compiler and its own PA38
object root. If one worktree is used, rebuild `dev/cppgm++` with the intended
host compiler before starting that lane, or build PA-local/scratch compiler
binaries that make the selected compiler explicit.

Use a host-control run only to distinguish harness/build issues from compiler
output bugs:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 \
make -C pa38 test-through-pa10 \
  CXX="$CLANG_CXX" \
  CPPGM_HOST_CXX="$CLANG_CXX" \
  PA38_OBJ_ROOT_BASE=../obj/pa38-host-control-clang
```

The host-control run should not replace either self-host frontier. If
host-control passes and a self-host lane fails, treat the symptom as a compiler
output bug until proven otherwise.

## Homebrew GCC Frontier

Use the Homebrew GCC toolchain as a separate hosted-header frontier without
clobbering the clang-built `obj/` tree:

```sh
GCC_CXX=/usr/local/opt/gcc/bin/g++-15
GCC_OBJ=../obj/gcc15
```

Build PA-local GCC `cppgm++` binaries so the report uses `./cppgm++` inside each
assignment directory and leaves `dev/cppgm++` as the clang-built primary tool:

```sh
make -C pa34 cppgm++ CXX="$GCC_CXX" CPPGM_HOST_CXX="$GCC_CXX" OBJ="$GCC_OBJ"
make -C pa35 cppgm++ CXX="$GCC_CXX" CPPGM_HOST_CXX="$GCC_CXX" OBJ="$GCC_OBJ"
```

Run the hosted report from the repository root, passing the selected assignments
to the report wrapper rather than invoking a single PA directly:

```sh
CPPGM_TEST_APP=./cppgm++ \
make test-report-nobuild \
  ACTIVE_TEST_REPORT_PAS='pa34 pa35' \
  CXX="$GCC_CXX" \
  CPPGM_HOST_CXX="$GCC_CXX" \
  OBJ="$GCC_OBJ" \
  ORDERED=false
```

If a fix adds or changes a checked-in test, validate that owner regression with
the clang-built compiler as well. Use the GCC report to expose GCC/libstdc++
frontier failures, but keep regressions environment-agnostic unless the feature
itself is hosted or vendor-specific. Audited type-text fallbacks are strict by
default, so libstdc++ progress should come from structured type resolution, not
from recovered text.

For the PA38 GCC self-host frontier, keep a separate object root from the clang
PA38 ladder. If a run is resource-sensitive, cap both make's autodetected job
count and the test harness workers explicitly:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 CPPGM_TEST_JOBS=4 \
make -C pa38 test-through-pa10 \
  CXX=../dev/cppgm++ \
  CPPGM_HOST_CXX="$GCC_CXX" \
  PA38_OBJ_ROOT_BASE="$GCC_PA38_OBJ" \
  DEFAULT_BUILD_JOBS=4
```

## Frontier Order

Work in the same order as the PA38 target:

1. self-host compile failures while building checkpoint objects
2. self-host link failures while producing staged binaries
3. `pa1` test failures under `pptoken-self`
4. `pa2` test failures under `posttoken-self`
5. `pa3` test failures under `ctrlexpr-self`
6. `pa4` test failures under `macro-self`
7. `pa5` test failures under `preproc-self`
8. `pa6` test failures under `recog-self`
9. `pa7` test failures under `nsdecl-self`
10. `pa8` test failures under `nsinit-self`
11. `pa9` test failures under `cy86-self`
12. `pa10` tests under `cppgm++-self --emit-ast`

Stop at the first real failure. Do not scan ahead while the current frontier is
unreduced.

## Failure Workflow

For each failure:

1. Reproduce with the smallest PA38 command, then with the smallest direct
   compile/test invocation that preserves the failure.
2. Classify the failure as compile, link, runtime, exit-code, LowIR direct text
   drift, or timeout.
3. Determine whether the visible symptom is the root bug or only fallout from
   an earlier compile/lowering/runtime issue.
4. Reduce away self-host scale and hosted-library noise where possible.
5. Choose the earliest owning PA based on the underlying feature, not on the
   PA38 rung that exposed it.
6. Add a minimal durable regression in that owner before or with the fix.
7. Fix the implementation in `dev/`.
8. Validate the owner regression and owner suite.
9. Rerun the active PA38 frontier with
   `CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1`.
10. Commit the coherent fix batch before moving to an unrelated failure.

Do not change a PA38 test, skip a self-host stage, loosen comparison, or alter
the self-host wrapper just to get past a failure. If the self-host target
exposes bad output, reduce and fix the underlying compiler bug.

## Regression Placement

Use the same ownership rule as the PA34/PA35 process:

- tokenizer/preprocessor bugs belong in `pa1` through `pa5`
- parser/AST bugs exposed by `cppgm++ --emit-ast` usually belong in `pa10`
- type/semantic/lowering bugs belong in the earliest PA that introduced the
  feature in `ROADMAP.md`
- LowIR text drift under direct compare belongs to the emitting/lowering PA
  that owns the exact output contract
- host object/link/runtime ABI issues belong in `pa32`/`pa33`/`pa35` as
  appropriate
- PA38 should keep only true self-host integration proofs

The regression source must stay environment-agnostic. It is acceptable if a
bug only reproduces under one host compiler or ABI setup, but the test should
not encode that setup unless the tested feature is explicitly hosted or
vendor-specific.

## Debugging Tools And Tactics

When the failed source is still large, prefer scripted traces before ad hoc
manual debugging:

```sh
python3 scripts/bootstrap_trace_report.py \
  --repo-root . \
  --trace-source /tmp/reduced.cpp \
  --preset template-lifecycle \
  --focus '<symbol-or-template>' \
  --write-prefix /tmp/pa38-pa10-<tag>
```

Useful presets:

- `template-lifecycle` for overload, deduction, instantiation, and template
  ownership failures
- `output-lifecycle` for missing or extra emitted functions, variables, and
  template instantiations
- `full-link-root-cause` for mixed compile/link failures

For a single self-host source compile after a lane has warmed its PA38 object
root, reuse that lane's object root instead of creating a fresh one. Use the
same host compiler as the lane being debugged:

```sh
python3 scripts/report_self_compile_sweep.py \
  --repo-root . \
  --compiler ./dev/cppgm++ \
  --host-cxx "$CLANG_CXX" \
  --frontend cppgm++ \
  --object-layout pa38-selfhost \
  --build-dir ./obj/pa38-clang/selfhost \
  --test-runner 1 \
  --timeout-sec 0 \
  --source dev/src/<failing>.cpp \
  --output-prefix /tmp/pa38-pa10-<tag>
```

For runtime divergence, compare the smallest host-built and self-host-built
binary behavior first. If a diagnostic changes the behavior, assume the bug may
be layout-sensitive and debug the original binary rather than trusting the
instrumented result.

## Validation Cadence

Per fix:

```sh
make -C <owner-pa> check TEST=<new-regression> \
  CXX=/usr/local/opt/llvm/bin/clang++ \
  CPPGM_HOST_CXX=/usr/local/opt/llvm/bin/clang++
```

Then run the owner suite or targeted strict/report gate appropriate to the
owner. For PA10+ owner tests, prefer the existing strict/report harness when it
gives faster all-failure visibility.

For the active frontier, run clang first:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 \
make -C pa38 test-through-pa10 \
  CXX=../dev/cppgm++ \
  CPPGM_HOST_CXX="$CLANG_CXX" \
  PA38_OBJ_ROOT_BASE="$CLANG_PA38_OBJ"
```

Then validate the same state in the GCC lane:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 \
make -C pa38 test-through-pa10 \
  CXX=../dev/cppgm++ \
  CPPGM_HOST_CXX="$GCC_CXX" \
  PA38_OBJ_ROOT_BASE="$GCC_PA38_OBJ"
```

Before each commit:

- `git diff --check`
- focused owner regression and owner suite pass
- active clang PA38 frontier has moved or is green for the fixed failure
- active GCC PA38 frontier has either moved/green for the same failure or the
  fix has been validated with an equivalent focused GCC object/test command
- staged files contain only the intended fix batch

After each coherent batch:

```sh
git commit -m "<short fix summary>"
```
