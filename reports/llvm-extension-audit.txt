LLVM optimization extension audit, 2026-11-09
============================================

Three gaps are fixed and fully qualified: repeatable GNU pure/const calls,
fixed-width bit reversal and non-null pointer return promises. Remaining gaps
include allocator return-alias promises, restrict, alignment, minsize and
visibility. The extension group alone measured 0.8331x native with essentially unchanged
retired instructions. A subsequent boolean/conversion group measured 0.8130x
(native 43.615 s, cppgm-built 53.650 s), with 0.2823% fewer retired instructions
than the extension checkpoint and essentially unchanged cppgm-built elapsed
time. The readable-parameter/tail-sharing follow-up measures 0.8264x, with
0.0775% fewer instructions than the boolean checkpoint and essentially
unchanged cppgm-built elapsed time. None achieves the 0.95x objective.

Scope and evidence
------------------
Audited the exact 2577 C++ translation units feeding the LLVM 22.1.2
clang-22 target, plus their 5696 source/generated-header dependency closure.
The native and cppgm builds use identical source hashes and generated header
contents. Dependency discovery uses the native build: the cppgm object
dependency entries are empty and cannot establish header coverage.

Evidence is retained outside the checkout under
/mnt/vizier/cppgm-llvm-evidence/llvm-extension-audit:
clang-target-complete-inventory.json, source-feature-queries.json,
attributes-final.lowir, repeated-effects-results.json and the disassemblies.
The inventory counts lexical occurrences, including inactive code, comments
and strings; it is not a count of active annotated declarations. We separately
compared the 56 source-spelled feature queries and expanded Compiler.h macros
with the actual LLVM compilation configuration.

Findings at the accepted B26 checkpoint
--------------------------------------
* always_inline (142 LLVM macro occurrences) and noinline (54) are retained
  and consumed. Template instantiations consult their primary/pattern inline
  attributes. LLVM_LIKELY/UNLIKELY reach branch probability metadata.
* LLVM_READONLY (589) and LLVM_READNONE (14) become read-only/read-none memory
  effects. The baseline does not reuse repeated calls: a reduced pure/const
  example emits two calls with cppgm versus one with GCC 15 and Clang 22.
  Memory effects alone are insufficient to authorize reuse: read-only LowIR
  calls can perform IO. A separate repeatability fact is needed for the GNU
  pure/const promise, with memory writes and opaque/non-memory barriers handled.
* LLVM_ATTRIBUTE_RETURNS_NONNULL (65) is disabled by our feature query.
  LLVM_ATTRIBUTE_RETURNS_NOALIAS (6) expands to GNU malloc, which the parser
  accepts without retaining its return-alias promise. These lose useful
  pointer facts. A malloc attribute does not imply no global memory writes;
  it must not be treated as an existing builtin allocator's memory effects.
* __restrict/__restrict__ are discarded lexically; LLVM_ATTRIBUTE_RESTRICT
  occurs four times, including the GlobalISel decoder. No parameter no-alias
  fact reaches the optimizer.
* LLVM_ASSUME_ALIGNED (10) is advertised, but lowering currently returns the
  pointer and discards the alignment/offset promise. Its uses are in Endian.h;
  scalar unaligned x86 accesses may already have the same instruction cost.
* LLVM_ATTRIBUTE_MINSIZE (5) and visibility macros (15 combined) select
  fallbacks because our feature queries answer false. Size optimization and
  symbol visibility need distinct implementation/measurement; accepting their
  spelling alone would not implement the requested behavior.
* __builtin_bitreverse8/16/32/64 queries answer false. MathExtras.h therefore
  selects byte-table reversal with copies and a loop. This is an actual
  algorithm fallback worth reducing and measuring.
* LLVM_PREFETCH has two lexical occurrences, both in its macro definition;
  no actual LLVM source use was found in this closure. Dropping that hint is
  not evidence of a slowdown in this workload.
* Other query differences include diagnostic/debug/sanitizer annotations,
  platform-specific calling conventions and fallthrough annotations. Their
  lexical presence is not evidence that they affect this X86 Release build.
  In particular, the cold/hot/flatten spellings found by this scan are in
  generated Clang attribute tables/documentation, not active GNU annotations
  on the compiler functions being built.

Completed changes and qualification
------------------------------------
GNU repeatable scalar calls (3dd0515ee), fixed-width bit reversal (2c26e2566)
and non-null return promises (399e1c762) have passed together:
* strict 9949/9949, debug/modern, all architecture/file/placement/CWG audits,
  harness, PA5 self-host and inception;
* student export, all 42 reference-wrapper checks, all 13 new exported
  fixtures, PA35 quick/smoke and the official course/student releases 17/17;
* frozen compile instructions 0.9998385x O0 and 1.0019531x O3 (+0.1953%), with
  RSS below the parent in both cases;
* all 2577 LLVM C++ units, without fallback, in a fresh 3163-step build taking
  355.87 seconds; all 204 generated dependencies in the audited closure match
  the native build;
* all 323 current cppgm objects and linked compiler byte-identical between
  native-built and cppgm-built Clang; separately, all 323 frozen objects and
  the linked compiler match, including every timing observation.

Fixtures cover stores, volatile/opaque calls, by-value object arguments,
pointer-call and specialization controls, signed/narrow argument conversion,
all four bit widths, constant evaluation, and single operand evaluation.
GCC/Clang runtime oracles pass; bit-reversal spellings are checked against
Clang because GCC 15 does not provide them. The non-null reduction removes
three comparisons while preserving calls and the unannotated controls.
Explicit specialization attribute ownership follows GCC 15; Clang 22
inherits returns_nonnull here. Shared runtime fixtures are valid under both
interpretations, and this difference is retained in the oracle evidence.

Five existing references were regenerated through normal reference commands
to record repeatable=yes; changes are only boundary facts. The initial full
release missed course timing headroom (2.44x versus the 2.40x margin target;
hard limit 3.00x). The unchanged-build cached rerun passes: course 2.10x,
student 1.78x. Both failed and passed observations are retained.

Full runtime comparison and next work
-------------------------------------
The frozen 323-unit ABBA comparison gives native 44.715 s versus cppgm-built
53.675 s: speed ratio 0.8330694x. CPU ratio is 0.8354309x. A/A observations,
all outputs and user-mode counters are retained; counter coverage is 100%.
Cppgm-built Clang retires 1.238604 trillion instructions versus 1.238735
trillion at B26 (0.99989384x); native instructions remain stable. This is no
resolved instruction-count improvement, despite useful local reductions.

Four-unit private relinks took 8-24 seconds and also showed no resolved
downstream win. They are quick localization experiments, not full scores.
Fresh instruction/LBR profiles are in block27-runtime-profile. Forcing an
aggregate getter inline in a one-object private link did not improve its
sample; native Clang also leaves that getter outlined. Do not promote that
header override or mistake symbol-attribution movement for saved work.

The acceptance receipt is block27-attributes-qualification-state.json in the
evidence directory. Continue with measured hot-path reductions, batching
three or four supported improvements for each full rebuild. Investigate the
remaining extension promises where active hot code uses them; accepting or
advertising a spelling alone does not implement its optimization semantics.

Remaining-promise reductions, B33 candidate
------------------------------------------
A fresh probe includes the pinned llvm/Support/Compiler.h with the Release
C++17 configuration and compares the immutable B33 compiler with GCC 15.2
and Clang 22.1.2. All three compile it successfully. The retained source,
commands and outputs are llvm-extension-audit/remaining-promises* and
{cppgm,clang,gcc}-remaining-promises* in the evidence directory.

* LLVM_ATTRIBUTE_RETURNS_NOALIAS on an allocator leaves two potentially
  aliasing loads around a store through the returned pointer. GCC/Clang
  retain one load and also eliminate the dead allocation-result store.
  The active source use is allocate_buffer in Support/MemAlloc.h and .cpp.
  This promise describes result aliasing, not the allocator's global effects.
* LLVM_ATTRIBUTE_RESTRICT leaves two loads around a store through a distinct
  restricted pointer, versus one load with GCC/Clang. The non-definition
  LLVM use in the audited closure is fastDecodeULEB128 in the GlobalISel
  match-table executor; its presence does not establish a hot-path benefit
  for this X86 SelectionDAG compilation workload.
* LLVM_ASSUME_ALIGNED(p,64) loses the promise: converting the returned
  pointer to an integer and masking by 63 remains an operation, whereas
  GCC/Clang return zero. The actual LLVM uses are five memcpy pointer
  arguments in Support/Endian.h; scalar x86 unaligned loads can still
  have the same instruction cost. This is a proven lost fact, not a
  measured explanation for the overall runtime gap.
* [[gnu::const]] is preserved and the reduced repeated call is reused,
  matching GCC/Clang. clang/Format/Format.h uses this scoped spelling; there is no
  additional missing-attribute gap for it.

These remaining facts are not fixed by B33's readable-parameter propagation
and machine-tail sharing. They remain candidates for separate normal PA
regressions and measured fixes. In particular, do not advertise support
through a feature query merely because the parser accepts an attribute.

Active alignment-use check
--------------------------
An additional reduction calls the actual pinned Support/Endian.h aligned
and unaligned 64-bit little-endian readers and writers. GCC, Clang and B33
all pass the 4096-value runtime check at O0 and O3 (six successful runs).
At O3, all four B33 functions have exactly the same scalar mov/ret code as
Clang. The lost alignment fact is real, but it does not add instructions in
these representative active LLVM uses. Evidence: endian-active-uses.cpp,
endian-active-uses-results.json, endian-active-objects-results.json and
*-endian-active-uses-O3-object.asm in the evidence audit directory. The
executable-only disassembly is not used: cppgm's standalone executable
omits its symbol table; the separately compiled objects carry the symbols.

Supplemental source check at B38
--------------------------------
Recompiling remaining-promises.cpp with the immutable B38 compiler produces
exactly the same optimized LowIR as B33. The allocator return-alias,
restrict and assumed-alignment gaps therefore remain present; scoped GNU
const call reuse still works. Evidence: remaining-promises-block38-results.json
and cppgm-block38-remaining-promises.lowir in the audit evidence directory.
All 204 generated dependencies in the authoritative native header closure
also match the fresh B38 LLVM build byte for byte.

A supplemental scan checks raw GNU/scoped attributes, builtins and pragmas
outside Compiler.h's wrapper names. Its lexical candidates are retained in
source-extension-lexical-supplement.json and source-extension-pragmas.json.
These are candidate lists, not active declaration counts: LLVM contains
generated attribute documentation, literal code examples and other platforms'
disabled branches. The xxhash may_alias typedef and explicit clang loop
unroll(full) pragma occur inside LLVM_XXH_USE_NEON, disabled in this X86
configuration. CrashRecoveryContext's optnone annotation is confined to
the MSVC/32-bit branch. Neither supplies a missing active optimization hint
for the measured build. The compiler already recognizes may_alias and pack;
ordinary unknown pragmas are ignored. The scan found no additional active
loop-unroll request in this source/header closure.

Keep the remaining promises as separate, measured work. In particular,
malloc describes aliasing of the returned pointer and does not authorize
discarding the allocator's global writes. Restrict needs its scoped access
rules; it cannot be implemented by blindly marking every pointer parameter
pairwise disjoint. An alignment feature query should only promise the
alignment semantics actually preserved by lowering and optimization.

The B38 result-storage group is now qualified: strict 9976/9976, all required
audits, debug/modern, PA5/inception, export/wrappers/fixtures, quick/smoke,
both full releases 17/17 and the frozen compile gate pass. All current and
frozen LLVM-generated cppgm objects and linked compilers match byte for byte.
Its full runtime score is 0.80835x (43.295 s native, 53.560 s cppgm-built),
with 0.0667% fewer cppgm-built instructions than B33 and essentially unchanged
elapsed time. The first student scaling observation missed release headroom;
the same-binary speed-only recheck passes (2.23x, course 2.13x), with both
observations retained. Acceptance receipt: block38-result-values-qualification-state.json.
This qualification does not fix the remaining extension promises above.

B44 allocator return-alias candidate
------------------------------------
The active GNU argumentless malloc promise is now retained as the independent
LowIR boundary fact noalias_result=yes, including reserved/scoped spellings,
redeclarations, implicit template instances and virtual call boundaries.
Explicit specializations use their own declarations; ordinary function
pointer types acquire no declaration attribute. The argument-bearing
deallocator-association form alone supplies no alias promise. Call writes,
possible null returns and unwinding remain independent. The optimizer uses
the return promise for storage identity while retaining conservative effects
across the call.

Normal PA8 model/negative fixtures, PA28 runtime interoperability, PA32 source
ownership and raw/source alias predicates cover the change. Both alias and
recursive-visitor predicates fail on immutable B41 and pass on the candidate.
GCC 15, Clang 22 and candidate runtime checks pass at O0 through O3; per-pass
verification and source replay pass too. The isolated allocator change leaves
all 64 sampled LLVM objects byte-identical: no downstream speedup is claimed
for that attribute alone. The grouped B44 candidate remains under full LLVM
and release qualification; accepted compat/llvm remains B41.

Primary semantic source:
https://gcc.gnu.org/onlinedocs/gcc/Common-Attributes.html#index-malloc-function-attribute

Restrict, assumed alignment, minsize and visibility remain separate gaps.
