Objective and completion boundary

Systematically discover and repair C++ correctness defects exposed by pinned
GCC and Clang compiler tests, using the repository's normal PA regression,
compiler implementation, correctness, architecture and performance workflow.

Grade acceptance of valid programs, required diagnosis of ill-formed programs,
and required link/runtime/output behavior. Do not grade diagnostic wording,
number, location, notes, recovery or optional warnings. Those upstream checks
are retained as annotations, not compiler repair requirements. A normal
required diagnostic is sufficient for a whole negative translation unit;
reduced single-rule negatives and valid neighboring controls are needed to
establish coverage of individual rules. A crash never satisfies a negative.

Record original C++11, later CWG/DR resolutions, deliberate extensions,
ill-formed-no-diagnostic-required cases, implementation-defined/unspecified
behavior and unresolved standards questions separately. Both acceptance and
rejection may be permitted for a no-diagnostic-required case; its vendor
expectation cannot create a required language diagnostic. Host agreement
supports investigation but does not replace a standards basis.

“All gaps” means complete accounting of a declared upstream corpus and its
applicable test configurations. No finite suite proves complete C++11
conformance. Close each discovered defect and explain each excluded case;
never infer completeness from the current source-acceptance percentages.
Repairs and harness work follow this plan. Existing native diagnostic scores
are historical oracle-compatibility measurements, not C++ correctness rates.

Deliverables

- Versioned corpus manifest with source revisions, paths/hashes, test variants,
  target/dialect settings and licenses. Preserve original upstream sources.
- External runner with explicit coverage/skip reasons and validated metadata
  handling; retain the current personal scripts as the initial survey.
- Machine-readable observations and a deduplicated root-cause issue ledger.
- Focused regression/fix changes in the owning PA and dev modules, with full
  correctness and performance evidence for every fix.
- Final coverage matrix, unresolved limitations, and reproducible rerun commands.

Stage 1 — build an exhaustive inventory for the declared scope

1. Inventory the complete GCC C++ compiler test directories, including g++.dg
   beyond cpp0x and applicable g++.old-deja cases. cpp0x is only a starting
   cluster; C++11-relevant ABI, lookup, parser and template regressions occur
   elsewhere. Include preprocessing inputs and referenced headers, companion
   translation units and helper files. Inventory targets before downloading
   large unrelated trees; record explicitly excluded non-C++ test families.
2. Inventory Clang CXX (including defect reports), SemaCXX, SemaTemplate,
   Parser, Lexer, Preprocessor and CodeGenCXX plus applicable C++ inputs in
   other compiler directories. Select by metadata/actual C++11 applicability,
   not just filenames or the presence of '-std=c++11' text. Include tests
   whose defaults apply to C++11 and every relevant RUN-line variant.
3. Freeze the first coverage scope to x86-64 Linux, ISO C++11 and GNU C++11
   as separate dialects, the pinned host library, and supported optimization
   levels. Inventory other targets/configurations as explicit exclusions.
   Track standard defect resolutions separately from later language features.
   Prioritize original C++11/N3485 contract defects; label later CWG/DR
   compatibility separately rather than counting it as original conformance.
4. Keep standard-library test projects as a separately inventoried expansion:
   GCC libstdc++ and LLVM libc++. They require their own library configuration,
   test support and expected failures. Do not mix their scores with core
   compiler tests. Add macOS and alternate host-library cells after Linux core
   coverage has reliable oracles; retain them in the declared coverage roadmap.
5. Every candidate must have a disposition: supported check scheduled/executed,
   harness-blocked, outside declared scope, intentional course extension,
   upstream/host problem or unresolved. Unknown directives remain visible
   blockers. A directory-wide skip cannot stand in for per-case inventory.

Stage 2 — make the external oracle trustworthy

Prefer upstream DejaGnu metadata evaluation for GCC. If an adapter supports a
restricted grammar, reject unsupported directives explicitly. Honor dg-do,
language/target selectors, effective-target requirements, options, additional
sources and expected failures. Use active diagnostic directives to identify
potential negative cases, then adjudicate the rule and retain diagnostic
presence as the candidate check. Project dg-final requirements onto behavior,
ABI or objects when possible; preserve unsupported output checks as coverage
gaps. Diagnostic regexes/counts remain metadata only.
Force the selected C++11 dialect; never silently run a test in a newer mode.
Probe effective targets using the candidate's real capabilities. Accepted but
ignored -f/-m/-W flags do not establish support.

Use a dedicated Clang lit configuration/adapter for applicable RUN lines.
Preserve substitutions, target triples, includes, split-file setup,
REQUIRES/UNSUPPORTED/XFAIL and standard-specific verify prefixes. Do not
redirect arbitrary %clang_cc1 commands to the cppgm driver. Use active
standard-specific expected-error directives to discover negative cases, not
to require Clang's diagnostic spelling, locations, counts or recovery. Remove
-verify and its control options from candidate invocations. Classify each
RUN line's actual language/behavior obligation; unsupported AST/IR checks
remain explicit gaps until an equivalent independent oracle is implemented.

For each case distinguish preprocessing, semantic analysis, object generation,
linking and execution. Run positive syntax cases through object generation
where applicable: syntax-only acceptance misses deferred/emission failures.
Compile cppgm host objects with -c and link hosted programs using the host
compiler driver. Test multiple translation units and ABI interaction when the
case calls for them. Exercise supported -O0/-O1/-O2/-O3 configurations at the
appropriate external lane, without adding optimizer requirements to early PAs.

cppgm currently rejects GCC's -S and Clang's -cc1/-verify/-emit-llvm. Translate
only semantically equivalent checks. AST/LLVM IR/assembly checks that cannot
be run remain harness/output-interface coverage gaps. Where practical add an
independent behavior/ABI/object check, recording it as adapted coverage, not
an upstream textual-check pass. Genuine codegen requirements remain open
until tested. No implementation of an LLVM IR backend is implied by this plan.

Validate the adapter against small metadata cases and upstream host compilers
before trusting candidate totals. Run make test-harness after runner changes;
include fixtures that exercise conditional diagnostics, xfails, skips, extra
sources, crashes, timeouts and unavailable checker interfaces. Keep upstream
baseline failures separate from candidate failures.

Mixed positive/negative source files need isolated, faithfully reduced subcases
and positive mirrors: rejecting a whole file does not test all of its valid
paths or prove every invalid construct is diagnosed. Establish each reduced
case's required outcome from the relevant language rule. For negative cases,
check normal compiler termination and a diagnostic from compilation, excluding
linker output, capability probes and driver usage errors. A diagnosed extension
may be accepted. For positive cases retain successful compilation, linking,
execution and output checks as applicable. Signals, timeout and internal error
70 always fail a negative case. Warning-escalation options require reviewed
language-only replay; an optional warning promoted by -Werror is not a language
error. Keep IFNDR, extensions and unresolved cases outside the graded denominator.

First rescore immutable native receipts as a provisional language-outcome
screen, keeping all raw evidence and native assertions. Show matches,
mismatches, blocked cases, standards dispositions and coverage separately.
This screen is not a complete conformance result: individual negative rules
still require isolation and positive controls. Then replay with correctness
projections and expand beyond the initially selected problem cohort. Publish
separate positive-compile, required-negative, runtime/ABI and whole-corpus
coverage counts; never present the old 3.6% diagnostic-parity score as C++
correctness. Clang remains unmeasured until its language projections execute.

Stage 3 — triage all findings and fill discovery blind spots

First reproduce every current mismatch with its intended options and target.
Cross-check GCC and Clang, then adjudicate against C++11/course requirements;
host agreement is evidence, not the specification. In particular PA20 accepts
some C++14 auto-return forms in C++11: record that deliberate extension rather
than breaking the handout to force host agreement. Changes to a deliberate
language policy are separate explicit scope decisions.

Group symptoms by demonstrated root cause, retaining all source/variant links.
Reduce crashes, wrong code, missing diagnostics and performance pathologies.
A reducer predicate must preserve the intended failure: a runtime defect must
not reduce to a compile rejection; a missing diagnostic must not become UB.
Check both low-level facts and runtime behavior to separate semantics,
lowering, optimization, ABI, backend, driver and harness faults.

After initial disagreements, inspect cases both compilers reject, currently
unexecuted variants, warning checks, and positives accepted only in syntax
mode. Expand to the full inventory, including other C++11 feature directories,
defect-report tests, multi-TU tests and applicable optimization configurations.
Maintain a feature-by-phase-by-dialect matrix; add targeted neighboring cases
where upstream coverage or the reduction leaves a blind spot. Never close a
feature merely because one representative source works.

Stage 4 — normal regression/fix cycle, repeated for EVERY compiler issue

1. Read the owning handout and spec.md. Identify the earliest PA that owns all
   reduced requirements, in the feature cluster of the latest feature used.
   Backend-only defects may need a LowIR fixture in PA24; host integration in
   PA26-28; hosted headers in PA29-31; optimization in PA32-33. Do not default
   every imported source to PA29 or put required regressions in student.tests.
2. Add a small required fixture under that PA's tests/ in a lane its Makefile
   actually executes. For PA10-23 prefer existing self-checking controls with
   explicit expected exit/rejection when appropriate. Use semantic/IR checks
   only when they assert the relevant contract. Preserve attribution/provenance
   according to NOTICE, including upstream revision/path for adapted tests.
3. Demonstrate the fixture fails on the unmodified baseline for the expected
   reason, and retain the log. A negative fixture must not “pass” on a crash.
   Add valid neighboring cases and SFINAE/hard-error distinctions where needed.
   Timeouts/large-array issues need a bounded scaling/resource check in addition
   to ordinary behavior, integrated into an appropriate executed lane.
4. Fix shared compiler modules in dev/src (and dev entrypoints if necessary).
   Consume typed syntax/semantic facts, preserve canonical identity and deferred
   work, parse once, and avoid source/output reparsing or eager hot-path work.
   Keep dev/frontend_source_sets.mk current. No test-name special cases.
5. Show the new regression passes, then rerun every upstream reproducer linked
   to the issue with its intended flags and all relevant dialect/optimization
   variants. Record remaining symptoms as separate open issues.
6. Run the owning suite and the full required verification below. Generate
   necessary references only through documented tools after establishing the
   oracle; reference wrappers built from dev are not independent correctness
   evidence. Do not hand-edit references, .my files, logs or obj artifacts.
7. Complete per-fix performance validation below. Correctness does not excuse
   an unmeasured hot-path regression. Resolve regressions or report the issue
   still open; do not loosen benchmark gates or silently waive noisy results.
8. Keep each logical regression/fix reviewable with its evidence. Close only
   after all mandatory checks and the external reproducer pass. Update ledger
   and external results, then move to the next independent root cause.

Per-fix performance protocol

A. Before editing, preserve immutable A (parent baseline); build immutable B
   (candidate) with the same host compiler, flags, instrumentation and runtime.
   Hash both and retain build identities. Freeze source AND included headers,
   host headers/toolchain, options and environment. Do not benchmark against
   live dev/src input that changed with the implementation.
B. Use the existing frozen semantic_overload workload and its stable/include
   closure/PERF_EPOCH.json. Add representative already-correct feature workloads
   relevant to the change and frozen representative hosted/self-host workloads.
   For changes to templates, constant evaluation or initialization, include
   bounded scaling variants and record max RSS. Self-host throughput must be
   measured when the fix can affect it, with frozen compiler input trees.
C. On this Linux host use scripts/run_ab_compile_benchmark.py. Calibrate A/A
   first using the same immutable binary as A and B. Then run at least 10 paired
   ABBA blocks per selected workload with predeclared warmup/load controls.
   Batch very short inputs so process startup/timer granularity does not dominate;
   document batching and apply the identical procedure to A/A and A/B.
   Retain every observation, including failed/contended blocks and exclusions.
   Do not benchmark concurrently with builds, suites or another benchmark.
D. Record wall/user/system time, peak RSS, output sizes/hashes and load/pressure
   snapshots. Measure allocation/instruction counts when the change plausibly
   affects them and an appropriate profiler/counter is available; record tool
   and availability, never substitute an unsupported counter claim. On macOS
   run scripts/validate_perf_regression.py against the existing hardware-counter
   gates. Linux wall-time evidence does not replace a claimed macOS gate pass.
   With hardware counters available, use paired retired-instruction counts as
   the primary compiler-work measure under load (user steering, 2026-11-05).
   Calibrate A/A counters, verify scheduling/multiplexing, and retain timing
   and RSS. Noisy wall time stays explicitly inconclusive; reliable counter
   and memory gates can establish the performance result without pretending
   timing passed. Predeclare counter tolerances before inspecting A/B data.
   Measure compiler-process RSS separately from profiler/runner RSS: a larger
   wrapper can hide changes in a smaller child. Validate that scope with a
   touched-allocation control checked against the child's own getrusage value.
   Keep whole-command resource data separately. When correcting measurement
   scope, retain prior observations and recheck the affected closed repairs;
   masked wrapper RSS does not prove the compiler's memory gate passed.
E. Predeclare workload tolerances and the statistical method using A/A noise and
   repository gates before inspecting A/B results. Report paired ratios and
   uncertainty; retain existing PA35 thresholds unchanged. A material regression
   outside the noise band requires investigation. If noise prevents a conclusion,
   improve isolation/measurement and repeat; do not record a pass.
F. Default to --output-mode exact on unchanged-correct workloads. A fix can
   legitimately change objects; in that case use deterministic mode plus an
   explicit independent semantic/ABI oracle and explain the expected difference.
   Determinism alone does not establish correctness. A baseline that crashes,
   rejects, times out or miscompiles the reproducer is not a comparable speed
   measurement: measure regression overhead on common correct workloads and
   report absolute cost/scaling of the newly supported case separately.
G. Attach immutable input/binary manifests, raw measurements, equality/oracle
   results, ratios, noise calibration and interpretation to the issue. Compare
   cumulative checkpoints with the original baseline to catch many small costs.

Checkpoints and final acceptance

After every fix: required PA regression passes; linked external cases pass;
full correctness/audits and applicable self-host/PA35 checks pass; per-fix
performance meets the calibrated gates; ledger has concrete evidence paths.

At each feature-family checkpoint: replay the entire supported external matrix,
compare with the original baseline, inspect new failures and unexpected passes,
and refresh counts without changing the denominator silently. Recheck closed
issues whenever a source revision, host toolchain or runner changes.

Declare the pinned core-compiler repair phase complete only when every inventoried
in-scope variant has executed its relevant oracle or has a documented approved
scope disposition; every confirmed in-scope compiler defect, including later
CWG/DR compatibility issues, is closed; no
unexplained crashes/timeouts, hidden negative-test failures or unmeasured fixes
remain; and final integrated correctness, export and performance checks pass.
Harness-blocked checks and intentional extensions are named coverage limits,
not successes. Library/target expansions have separate completion matrices.
Upstream revision refreshes start a new manifest/comparison cycle.


Stage 5 — upstream C++11 CI jobs and full-suite timing (user addition, 2026-11-06)

Start this final stage after all compiler issues have been fixed through the
normal PA regression, correctness and performance process, including the later
CWG/DR decisions. Their later date changes repair priority and classification;
it does not exempt them from this final repair gate. Keep the original N3485
and later-DR evidence separate throughout that work.

1. Create two new CI jobs, GCC C++11 tests and Clang C++11 tests, following the
   repository's existing CI conventions for pull requests, pushes and manual
   runs. Each job uses its validated upstream adapter: native GCC DejaGnu and
   the dedicated Clang lit/RUN adapter. Pin corpus and toolchain revisions,
   cache downloads by immutable identities, and retain source licenses and
   manifests. Choose runners, worker counts and timeouts from measured full-
   suite costs without reducing the declared coverage to fit a job budget.
2. Each job runs the complete applicable, declared C++11 matrix with cppgm and
   the matching upstream compiler: GCC for the GCC suite, Clang for the Clang
   suite. Preserve ISO/GNU11 configurations, target and optimization variants,
   applicable language expectations, xfails, required diagnostics and runtime
   checks through the validated correctness projections. Diagnostic parity
   is outside the CI acceptance criteria. Retain explicit
   per-case scope dispositions and interface adaptations. A compiler failure,
   crash, new skip, missing variant or adapter blocker must not silently shrink
   the workload or become a pass. Host baseline failures stay separate.
3. Alongside every CI run, benchmark the time to execute the entire suite with
   cppgm versus the matching upstream compiler. Freeze identical test inputs,
   applicable variants, dependencies, environment and worker counts. Time the
   complete test execution, including preprocessing, compilation, linking,
   execution and checking where applicable; record one-time compiler builds,
   downloads and setup separately. Document stage/adapter differences so a
   timing ratio cannot conceal different work.
4. Use paired ordering with a predeclared warmup/cache policy and A/A
   calibration, following the existing performance protocol. Retain every full-
   suite observation and the ordering. Record wall/user/system time, load and
   available resource/counter data. Always report full-suite elapsed times;
   under contention, keep uncertain timing conclusions inconclusive and use
   reliable calibrated counters as supplementary evidence when available.
   Record unavailable counters explicitly. If workers or shards are used,
   retain end-to-end suite makespan separately from summed worker/CPU time.
5. Publish a CI summary and machine-readable artifact for each suite containing
   both compilers' full-suite times, paired cppgm/upstream ratios and uncertainty,
   revisions/binary hashes, configuration, test/variant counts, outcomes,
   exclusions and raw per-test/full-run logs. Incomplete or failing runs retain
   their elapsed time and status; do not present them as successful comparable
   whole-suite timings. Timing is reported on every run; establish any future
   timing regression gate through calibration rather than inventing an
   upstream speed-ratio threshold.
6. Validate both jobs and benchmark/reporting paths, including controls for
   omitted tests, changed skips, compiler crashes/timeouts, upstream baseline
   failures, incomplete timings and noisy measurements. Run make test-harness
   for the CI harness changes and retain a successful execution of each job.

The repair-phase acceptance above enables this stage. The overall campaign is
complete only after both CI jobs and their full-suite timing comparisons are
implemented, exercised and verified as well as all earlier acceptance criteria.
