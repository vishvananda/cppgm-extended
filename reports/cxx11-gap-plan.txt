Objective and order of work

Validate our compiler's C++11 correctness with GCC and Clang compiler tests,
alongside the existing internal tests. Deliver two CI jobs first and use their
failures to drive the normal regression/fix/performance workflow. Developing
the jobs and repairing the compiler proceed together; CI is not a final stage
waiting for a separate exhaustive discovery or measurement campaign.

This revision follows the user's 2026-11-07 clarification. The previous plan
is retained at plan-history/cxx11-gap-plan-before-2026-11-07-ci-first.txt under
the evidence root. Existing compiler repairs, tests, inventories and results
remain useful. The custom calibration/RSS queues are historical evidence,
not prerequisites for these jobs or for returning to correctness work. They
remain stopped following the user's pause.

The deliverables

1. A GCC C++11 correctness CI job using applicable tests from pinned GCC.
2. A Clang C++11 correctness CI job using applicable tests from pinned Clang.
3. In each job, correctness results and elapsed time for the identical declared
   suite with cppgm and with that suite's matching upstream compiler, plus an
   explicitly defined performance ratio.
4. For compiler gaps found by those jobs: a regression in the normal required
   test format at the earliest owning PA, a compiler fix, the required internal
   checks and the normal frozen compile/self-compile performance gate.
5. Offline plain-text CWG decisions and necessary adopted-paper wording under
   doc/cwg/, with provenance, an index, student-export inclusion and coverage CI.

Step 1 - bring up both real CI jobs

Create the jobs using the repository's CI conventions. Start with meaningful,
reproducible C++11 coverage supported by the adapters, and expand that coverage
as integration proceeds. Use the existing corpus and runner work. A complete
inventory of every upstream target, driver and checker is not a prerequisite
for getting useful tests running in CI.

Initial pins already inventoried:
  GCC 15.2.0: 5115c7e447fc07457443df874bf57840e8316d5f
  LLVM 21.1.8: 2078da43e25a4623cab2d0d60decddf709aaea28

Pin test sources, toolchains and dependencies; cache by immutable identity and
retain source licenses. Initially use x86-64 Linux, with ISO/GNU C++11 and
supported optimization configurations represented explicitly. Tests intended
for later standards, other targets or unavailable facilities need a specific
coverage reason. Standard-library test projects are separate from these core
compiler jobs.

Each job freezes a manifest of the actual selected test/configuration records:
source and dependency hashes, dialect, target, options, setup, expected language
behavior and required compile/link/runtime checks. Selection must not depend on
whether cppgm currently passes. Preserve known failures; never obtain green CI
by silently dropping failing inputs or shrinking the manifest.

Reuse native DejaGnu metadata for GCC and native lit/RUN metadata for Clang
where needed to establish the test's real obligations. Honor relevant setup,
selectors, includes, additional translation units and dependencies. Adapt
compiler interfaces only when the language check remains equivalent. Unknown
requirements stay visible. Optional diagnostic/checker interfaces must not
prevent running the independently established C++11 language checks.

Do not create empty or placeholder jobs that report success without executing
the declared tests. During bring-up, real failures may remain visible while
their compiler or harness fixes are developed.

Step 2 - judge C++ correctness

For valid programs, require successful compilation and the test's applicable
link, execution, output and ABI behavior. For ill-formed programs requiring a
diagnostic, require a normal compiler diagnostic. A diagnosed extension can be
accepted; diagnostic wording, counts, locations, notes and recovery are not
parity requirements. Compiler crashes, timeouts, internal failures and linker
errors do not satisfy a required compiler diagnostic.

Keep optional warnings and upstream-specific AST/IR/assembly spellings as
annotations unless an independent language, object, ABI or runtime obligation
is established. Missing an interface is a coverage limitation, not a language
pass or an automatic reason to change our compiler.

Adjudicate disputed expectations against the language rules. Track original
C++11 wording, adopted later CWG/DR behavior, deliberate course extensions,
IFNDR and implementation-defined/unspecified outcomes separately. Preserve
the course's deliberate policies. Upstream agreement is useful evidence but
does not replace the language contract. A permitted program termination must
not waive successful compilation/linking or conceal a compiler failure.

Mixed positive/negative translation units can expose only a whole-file result.
When investigating a gap, isolate the relevant rule and add valid neighboring
controls rather than trying to match every upstream diagnostic.

Report selected and executed test/configuration counts, positive/negative and
runtime outcomes, compiler failures, baseline failures and coverage limitations.
Give pass rates only for the explicitly executed, graded manifest; report the
coverage size alongside them. Unexecuted, blocked and unresolved cases are not
passes. Retain logs and machine-readable per-case results for both compilers.

Step 3 - time the same suite with both compilers on every CI run

For example, if a job selects 1,000 applicable tests/configurations:
  - run all 1,000 with cppgm, check their outcomes, and record elapsed time;
  - run the same 1,000 with the matching GCC or Clang compiler, check their
    outcomes, and record elapsed time;
  - report both times, both outcome counts, and the ratio.

Define the reported ratio as:
  cppgm_over_upstream = cppgm_suite_elapsed / upstream_suite_elapsed
Lower is better for cppgm. Always display the raw elapsed times as well.

Use identical selected tests, semantic obligations, dependencies, dialects,
targets, optimization settings and worker counts. Capture the actual commands
and explain necessary interface adaptations. A skip, missing invocation or
changed variant cannot silently change one compiler's timed workload.

Time the entire test execution, including compilation, linking, program runs
and checking where applicable. Keep one-time source downloads, tool setup and
compiler builds separate. Use the same documented cache/warmup policy for the
two runs. Record suite makespan separately from summed compiler/worker CPU
time when parallel execution is used.

The normal CI comparison is one complete cppgm suite run and one complete
matching-upstream suite run. It does not require a new repeated A/A/ABBA or
kernel-RSS tracing campaign. Record ordering, worker count and load information
so timing is interpretable. Counters may supplement the report when readily
available; their absence must not prevent the two elapsed-time measurements.

Ensure both compiler runs and artifact collection happen even when one fails.
Retain failed/incomplete runs' status, counts and elapsed time. Clearly mark a
ratio from failed, incomplete or unequal work as non-comparable; do not present
it as a successful passing-suite performance result. Timing is reported on
every run; do not invent a new cppgm/upstream speed-ratio acceptance threshold.

Step 4 - normal repair loop for each compiler gap

1. Reproduce the CI failure with its actual source, options and configuration.
   Determine whether it is a compiler defect, an adapter problem or a disputed
   upstream expectation. Deduplicate symptoms by demonstrated root cause.
2. Read spec.md and the owning handout. Add a reduced regression under the
   earliest owning paN/tests/ in the cluster of the latest feature it uses,
   within a lane that assignment's Makefile actually runs. Use the repository's
   normal test format and preserve upstream attribution. Required regressions
   do not belong only in student.tests/ or external scratch directories.
3. Show that the parent compiler fails for the intended reason. Add valid
   neighbors or SFINAE/body distinctions when needed to establish the rule.
4. Fix the shared compiler implementation in dev/ and dev/src/. Consume typed
   facts, parse source once, preserve canonical identities and avoid speculative
   work on hot paths. Keep frontend source lists current when needed.
   When supporting a CWG decision, add its offline text/provenance and any adopted
   paper needed to read its wording; keep student_export_documents.txt current
   and run make audit-cwg-references. Unresolved references must be labeled.
5. Run the owning suite, linked upstream reproducer and required internal
   correctness/architecture checks. Re-run the affected CI cases on the actual
   integrated compiler, then the job's declared suite.
6. Run the normal performance regression gate on the existing frozen compile
   or self-compile workload. Preserve the usual baseline, source/header epoch,
   host/toolchain identity, settings, repetitions and thresholds. Investigate
   an actual failure of that gate; do not substitute a bespoke benchmark matrix.
7. Integrate the repair and update its regression, source revision, validation
   results and CI outcome. A functionally repaired isolated worktree is not a
   passing integrated CI compiler.

Normal correctness and performance checks

Follow AGENTS.md and TESTING_AND_REFERENCES.md for the change's required checks:
affected PA suite, strict report, debug-info checks, self-host through PA5,
architecture/file/placement audits, and harness/export checks when applicable.
Run inception for self-host changes and PA35 smoke for lowering, optimizer or
backend changes; retain the normal final PA35 release check.

Use the existing performance tools as documented:
  - scripts/validate_perf_regression.py for its supported frozen-workload
    hardware-counter gate, with its normal baseline and defaults;
  - the existing PA35 quick/seed-self workflow for frozen compile/self-compile
    checks, as appropriate to the change and host;
  - the established platform-supported counter path under load when needed.

Keep the normal gate's behavior and limits. Reuse immutable baselines and valid
cached measurements. The normal repair comparison uses the immutable actual
parent and candidate. Keep campaign-wide deltas against the original campaign
binary as reported data; do not add a second campaign-wide acceptance cap.
Existing per-change thresholds and PA35/self-compile limits remain unchanged. A few extra targeted resource/scaling checks are justified
when the failure itself is a scaling/resource bug, or the normal gate exposes
a regression; they are not mandatory for every language fix. Do not invent
per-family/historical comparisons, dozens of extra workloads, repeated
calibration stages or a new RSS collector as routine acceptance requirements.
If a normal measurement is unavailable or inconclusive, say so explicitly and
use the established supported host/path; do not record a fabricated pass.
